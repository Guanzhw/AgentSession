# Codex raw usage census checkpoint

`scripts/v3-codex-usage-census.mjs` is an independent, read-only first checkpoint for the 3.0 statistics gate. It reads explicit JSONL sources through Node streams; it does not import either the Viewer or Rust parser. The private 840-file corpus is not scanned by tests or by default.

Prepare a private manifest containing an absolute source root and exact source bytes and SHA-256 for every file:

```json
{"root":"D:\\private\\codex-snapshot","files":[{"path":"sessions/one.jsonl","bytes":1234,"sha256":"<64 lowercase hex digits>"}]}
```

Run `node scripts/v3-codex-usage-census.mjs <manifest.json> <checkpoint.json>` only against a deliberately selected source set. Standard output is the public census JSON. The checkpoint is private working data and is atomically replaced after each complete file. The tool rejects duplicate source aliases and any checkpoint or temporary checkpoint path that aliases a source or manifest path or file identity before writing. Temporary creation is exclusive; a stale temporary file produces an explicit error and is left for inspection. On restart, each completed file is streamed again for its exact hash before its census is reused. Changed bytes reject the run and clear that file's checkpoint entry. A changed manifest starts a new checkpoint. A malformed line reports its file index and line number without printing source text. No input source or manifest is opened for writing.

The report counts canonical `token_usage_record` and legacy `event_msg/token_count` rows separately. It classifies each usage field as missing, zero, positive, or invalid; records response-ID collisions, conflicting owner/usage facts, and missing response and explicit owner IDs. `threadHeaderDifferences` and `sessionHeaderDifferences` are separate counts: a child record can legitimately name its child thread while its `session_id` names a parent. The private checkpoint retains both hashes separately, with `null` when absent; the file's session-header hash remains separate evidence. `pairedLegacy` only counts legacy rows with a matching *prior value signature* in the same file. Matches are not consumed, so one canonical row can be a candidate for several legacy rows; neither `pairedLegacy` nor `ambiguousLegacyPairs` proves a mirror relationship. The report also retains hashed parent, agent path, spawn-call, and `NEW_TASK` IDs and the first task boundary line. Child usage is counted as before or at/after that marker only when a marker exists; `noTaskMarkerUsage` leaves the boundary unknown. These are placement observations, not usage ownership claims. All identifying strings are SHA-256 digests, and transcript bodies are omitted.

This checkpoint does not produce request ownership gold or token totals. It also discards individual legacy positions and numeric vectors, so request and token reconciliation requires a separate evidence extractor. Later arbitration must resolve repeated value signatures, missing owner IDs, child inheritance, and whether legacy-only rows represent distinct requests. It must then compare independently owned requests with the runtime stats projection across the complete frozen manifest.
