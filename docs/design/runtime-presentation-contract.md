### 2026-09-20 实页反馈：集中呈现

用户查看原生 DSH 团队历史后指出四个问题：连续执行重复铺开，模型与用量藏得过深，
桌面左侧没有目录，团队图与正文分离。以下要求取代此前“用量默认收起、协作主要在侧栏”
的视觉选择；既有工程验收保留，新的集中呈现按 R1–R4 实施并在真实页面验收。

**组织单位是一次回复的阅读段落。** 用户请求与补充保持清楚边界；相邻纯执行记录共享
一个紧凑入口，可读正文与关键转折保留各自位置。段内原始消息、工具和 reasoning 的归属及顺序保留。这个分组只改变展示，
不产生新的 provider turn、任务或 token 记录。

| 内容 | 集中后的默认呈现 | 展开与定位 |
| --- | --- | --- |
| 身份、时间、模型、用量 | 回复顶部一条紧凑信息栏，模型与输入/输出/缓存直接可见 | 多模型分项、请求明细与统计口径按需展开；上下文标为最后记录值，不累计相加 |
| 连续纯工具/已知过程消息 | 相邻过程合为一个“执行过程 · N 条”入口，取消重复助手标题和空白 | 按原消息顺序展开全部过程；搜索和原始链接展开并定位具体消息 |
| 面向用户或阶段未知的文本 | 原文按消息连续可读，身份、模型与用量使用紧凑信息行 | 只有已识别为过程的文本随过程折叠；不按措辞猜测最终回复 |
| 分工与合作 | 沿简洁正文分支深化；工作动作与结果是焦点，分别表达分派归属与成员交接 | 就地展开任务、成员往来及完整子历史，并可返回对应正文位置；大量成员按工作分组展开 |
| 异步与后台 | 分离和返回在发生位置保留紧凑标记，使用同一任务身份连接 | 跨回复延续的工作保留原位置；选中后查看相关过程及时间，不按每个 Agent 常驻一列 |
| 桌面目录 | 左侧常驻、默认展开，跟随当前阅读位置；以请求分组，回复与任务为下级 | 任务只列一次，更多消息可展开；继承背景不混入自身目录 |
| 工作 / 事件、原始记录 | 归入“更多 → 技术详情”，从默认正文底部移除两个孤立入口 | 保留完整访问与深链接，以“运行数据”“原始事件”等具体名称说明内容 |

协作呈现与成员目录不重复平铺同一批内容；大量成员的目录只承担搜索和选择。正文中的协作
只讲当前相关的合作，整个会话的关系概览仍可按需查看。分派、成员关系和消息交接用不同的
标签表达，不能把“主 Agent 安排两人”误画成“writer 创建 reviewer”。

用户要求进一步调研协作进入正文的方式。[协作呈现调研](inline-collaboration-research.md)
记录官方案例、候选与同内容比较步骤；“正文局部协作图”由既定形式改为候选。
2026-09-21 用户认为 A 相对简洁有条理，但关系不清；B 缺少视觉焦点，C 难理解且无法应对
几十名成员。下一版沿 A 深化分派、同级交接、异步返回三类关系，焦点放在工作动作与结果。
团队与异步不是互斥类型，两类关系可同时属于同一工作。具体见调研第 7 节。

### 2026-09-21 已确认方向：A＋乙，服务于 agent runtime 阅读

用户选择参考题中的 A（Raycast 式正文优先、集中而克制的阅读观感）＋乙（默认露出关键
分派、交接和返回，普通执行过程折叠）。用户已在 A＋乙样稿上确认继续，正式页面按此实施。
参考产品提供层级和密度的启发；页面结构、组件与交互由本产品的运行关系和完整历史决定。

- **阅读主线**：请求、回复、关键协作和上下文变化连续可读；模型与用量位于紧凑信息栏。
  常规工具循环合并为局部展开入口，工作目的与已记录结果是视觉焦点。
- **关系语义**：分派表示谁负责什么；交接表示谁把什么交给谁；异步连接表示同一工作从
  分出到返回的延续。三者使用动作文字、端点和局部连接区分；团队成员也可以异步工作。
- **原位展开**：从当前工作展开具体往来，再进入完整子历史；跨轮返回仍落在实际接收位置，
  并能回到原分派。主线中途做过的工作保持可读。
- **规模与身份**：围绕工作组织相关成员与交接，按需展开复杂关系；同一 Agent 可以参与
  多项工作，同一工作可以多次交接和返回。后台程序、子 Agent 与上下文产物按实际类型命名。

正式页面同时用原生团队合作、异步延续和普通问答检验这一方向：默认看懂工作如何进行，
展开后读完细节，成员增多时仍有清楚的阅读焦点。视觉参考与选择记录见
[协作调研第 8 节](inline-collaboration-research.md#8-真实产品参考选择2026-09-21)。

### 集中呈现的完整性与密度约束

回复分组不是一个吞掉所有转折的大折叠框。用户补充、可读结果、任务失败/中断、返回和上下文
变化在默认阅读层保持可见。跨轮异步关系保持自己的身份；完整正文、搜索、子历史和返回位置
继续沿用现有契约。用量合计仅计入本阅读段拥有的请求，子任务消耗单列。

视觉上保持正文可读字号，以减少重复标题、卡片层级和空白提高密度。使用一套正文行宽、
紧凑的次级元信息和局部关系强调色；短问答无需执行空壳或协作空框。

2026-09-23 用户确认按发言者左右区分：用户消息块靠正文右侧，使用克制的主题底色，
身份与时间靠块内右侧；Agent 消息保持左侧正文。用户块随短消息收窄，长消息限制行宽，
块内段落、列表、代码仍左对齐。相同规则用于内联子历史，消息顺序、目录锚点与成员侧轨保持。

## 1. 用户来这里做什么

AgentSession 是**面向人的会话与工作历史阅读器**。读者回到这里，是为了重新看懂一次对话、
Agent 做过的工作，以及它如何与其他 Agent、后台任务一起完成这件事。
默认像聊天阅读一样简洁；逐层展开后，可以读到完整过程。
读者应能在一个阅读上下文里回答：

1. 我提出了什么，agent 最终回答或交付了什么？
2. 期间把哪些工作交给了谁；哪些并行进行、后来继续、被中断或返回？
3. 中间做了什么、说了什么，结果怎样回到主会话；能否展开读完？
4. compact、memory 等发生后，记录中保存了什么结果和上下文？
5. 哪些是这次执行新产生的工作，哪些只是继承的背景？

“默认简洁”和“记录完整”同时成立：折叠改变可见密度，不改变记录归属、搜索范围和完整内容的可达性。
阅读顺序与运行关系可以不同；主线程继续工作时，后台分支保持自己的身份与生命周期。

### 面向人的界面与面向 Agent 的 MCP

2026-09-20 用户进一步明确：Web UI 的中心是**内容的完整呈现和人的理解**。
MCP 面向 Agent 提供结构化检索与读取；Web UI 则把相同内容组织成可以回看的会话。
两者共享可靠的数据基础，分别设计各自的呈现。

真实记录、准确关联、来源归属和覆盖范围是实现质量要求。普通读者通过自然的名称、原文和
交互理解内容，不需要先学习 evidence、protocol、canonical、projection 或 recorded/derived。
只有缺失实际影响当前内容时，就地说明“这段结果未保存在本地记录中”等具体情况；详细诊断
留在主动打开的技术详情中。

### 阅读层级

| 层级 | 读者看到什么 | 如何深入 |
| --- | --- | --- |
| 默认阅读 | 用户输入、Agent 回复，以及分派、收到结果、中断/恢复、上下文压缩等关键转折 | 就地展开“执行过程”“查看审查意见”“展开子任务会话”等具体入口 |
| 工作过程 | 中间说明、工具调用、与同一 Agent 的多轮沟通、子任务自己的完整会话 | 展开某条调用、某次往来或具体结果；子历史继续使用同一阅读层级 |
| 单项详情 | 完整工具参数与输出、日志、已保存的推理、附件、继承背景和上下文结果 | 长内容续读、搜索定位；可以返回原阅读位置 |
| 技术详情 | 原始事件、内部标识、关联依据、读取诊断和用量口径 | 次级菜单或对应内容的详情入口；供确有需要的读者检查 |

层级是逐步披露内容，不是将同一会话拆成几张各自不完整的页面。默认正文中的回复与结果保留
可读原文；过程折叠不影响全文搜索，命中后自动展开对应内容。用户可以只读一轮的请求和回复，
也可以逐条展开，重看这轮工作的完整经过。

### 用户语言与入口

入口名称直接说明即将读到的内容或发生的动作。标题应采用可读任务名、目的或角色；
内部路径和 ID 在详情中保留。结果有正文时先给可读摘录，并提供完整阅读入口。

| 内部概念 | 面向读者的呈现 |
| --- | --- |
| Evidence / Source | 按实际目标命名：“查看分派内容”“查看返回结果”“展开执行日志”；精确原始记录入口放在详情中 |
| Dispatch / Follow-up / Delivery | “交给……处理”“补充要求”“收到……的结果”；与同一任务的其他往来关联 |
| Work graph / nodes / protocol version | “任务与协作”：谁负责什么、彼此怎样协作；图中展示可读内容，技术计数放入详情 |
| Compact / memory artifact | “查看压缩后的上下文”“查看保存的记忆”；正文先于生成、匹配及读取诊断 |

这些名称由内容决定，不是统一替换词表。例如工具日志不应被改名成“审查意见”，
一个任务的最近回复也不应代替某次返回的具体内容。

## 2. 页面职责

| 页面或区域 | 读者任务 | 默认内容与组织 | 次级内容 |
| --- | --- | --- | --- |
| 会话库 Library | 找到要回看的工作 | 以可读标题为主，项目与最近记录时间为辅；日期分组；搜索和少量常用过滤 | Provider、协作规模、用量和诊断按需查看；已有紧凑列表作为密度选项 |
| 历史阅读页 Reader | 回看会话，理解 Agent 怎样工作 | 用户请求、agent 回复、关键转折；一条主阅读路径 | 就地展开工作过程、完整子会话和协作概览；技术详情再深入一层 |
| 用量 Statistics | 比较消耗及来源 | 明确范围、时间、provider 和统计口径的图表与可核对明细 | 各请求、会话、后台任务的构成 |
| 设置 Settings | 管理 viewer 的读取与使用方式 | 数据目录、语言、主题、恢复命令等现有设置按用途分组 | 运行诊断与需重启的说明 |

阅读页是完整内容的主入口。“任务与协作”帮助理解分工和往来；旧 Work / Events 的技术能力
从详情菜单进入，不再作为与会话阅读并列的默认目的地。
统计与设置有独立任务，保留独立页面；它们不承担解释单次运行的责任。

### 会话库的识别规则

- 标题依次使用 viewer 自定义标题、provider 可读标题、可用的首条用户请求摘录。
  摘录是原文截取，不自动生成结论。只有这些都不可用时，才显示“未命名会话”和短 ID。
- 页面标题最多占两行；完整标题和完整请求各自有可访问的查看入口。
- 主会话与有记录关系的后台会话合并为可展开的会话家族；独立打开后台会话仍保留返回来源入口。
  无法确认归属的会话保留独立可访问项。
- 默认每项只保留识别工作所需的信息；tokens、模型、时长等不以一串同权重徽章挤占标题。
- “最后记录为运行中”与真实进程在线分开表达；仅凭旧日志不能显示实时运行指示。

## 3. 内容与呈现矩阵

“默认”指普通阅读状态；“展开”指用户主动查看详情。以下是目标要求，不是现有能力清单。

| 内容 | 默认呈现 | 展开后 / 完整性 | 放置与关系 |
| --- | --- | --- | --- |
| 用户请求、后续补充 | 可读正文，清楚的请求边界 | 长文续读、原文与附件；保留结构化问答的原始来源 | 记录发生的位置；后续补充可发生在前次执行尚未结束时 |
| 结构化问答回复 | 按顺序显示“问题 / 你的回答”，保持一个用户消息；目录和预览采用同一可读内容 | 原始包装独立折叠；长问答续读；默认搜索只计算展示正文 | provider 提供已识别投影；保留原消息和 part ID，question ID 本身不推断工具关联 |
| Agent 面向用户的回复 | 正文为主体，保留段落、表格、代码和链接 | 完整正文、可用附件；原始记录次级 | 所属消息位置，不按“最后一段文本”猜测 final |
| 已明确标记的中间说明、工具循环 | 合并到“执行过程”，显示有依据的数量和异常提示 | 原顺序的 commentary、工具输入输出、reasoning | 附属于产生它们的消息；不能跨请求、结果返回或上下文变化吞并节点 |
| 未区分阶段的 agent 文本 | 保留可读正文 | 原始元数据可查 | 由 provider 证据决定阶段，不能根据措辞把正文藏起来 |
| 工具调用和执行结果 | 执行过程中的工具名、简短动作、已记录状态 | 完整参数、输出、错误、日志续读；长代码局部滚动 | 同一调用的输入与结果关联，归属原 assistant 消息 |
| Reasoning | 随所属消息或工具折叠 | 读取 provider 实际提供的文本 | 不移到后一个 assistant，不恢复未记录的推理 |
| Dispatch / 分派 | “交给谁做什么”的紧凑插入；显示可读任务名和目的摘录 | 完整分派内容、子会话；精确时间与原始记录次级 | 分派发生点；开启同一任务的后续追踪 |
| Message / Follow-up | 同一任务上的补充要求和回复；连续密集沟通可局部折叠 | 按发送者与接收者阅读每次完整往来 | 跨多轮延续原任务，不每次新建任务卡 |
| 子任务完成与父会话接收 | 区分“子任务产生结果”和“主会话收到结果”；有原文时显示结果摘录 | 相应完整结果、子会话历史和父侧收到的原始记录 | 完成点和接收点分别保留；不得把二者合成虚构的同一时刻 |
| Interrupt / 失败 / 缺少返回 | 在相关协作插入与执行过程入口给出明确文字 | 原始错误、最后记录、重试或后续恢复证据 | 已结束日志仍保留最后已知状态，不制造持续运行的动画 |
| 子会话、后台任务、swarm/team 成员 | 有来源的目的、角色或任务名；继承背景默认收起 | 就地展开完整自身历史；可独立打开 | 身份由 canonical 引用决定，不以名称相同合并不同任务 |
| 团队协作 | 正文集中显示相关成员、分工与交接，具体视觉形式待样稿选择；会话全局概览按需打开 | 就地阅读任务、完整往来与子历史，并返回对应正文 | 团队成员关系、分派关系、成员间通信分别表达；普通父子任务不自动命名为 team |
| 后台程序、异步执行 | 在转入后台处保留动作，在返回处呈现结果；主会话中间的工作继续可读 | 启动内容、日志、轮询/等待、结束与后续处理 | 同一程序/执行连续关联；与子 Agent 分开命名，最后保存的状态不冒充实时进程状态 |
| Compact | 所在位置的一行“上下文已压缩”，主动作是“查看压缩后的上下文” | 结果摘要、实际保留条目与完整续读；事件技术证据次级 | 放在记录支持的边界，不能统一搬到会话末尾 |
| Memory / dream / experience 等辅助工作 | 按记录中的实际目的显示；已知产出优先 | 完整产出、相关工作过程和自身历史；生成诊断次级 | 使用相同的后台工作呈现；名称本身不证明它修改了主会话上下文 |
| 继承背景 | “继承的背景”独立折叠入口，能说明来源时显示来源 | 完整可用背景、分页和长字段续读 | 不进入子会话自身历史的 ToC、默认搜索或新增用量 |
| 文件、产物和变更 | 已记录产物紧邻相关结果；短文件名可识别 | 完整路径、可访问链接、记录中的 diff 或附件 | 不把工具提到的每个路径推断为已交付产物；不可用时明确说明 |
| Tokens / 模型 / 上下文大小 | 在回复信息栏直接显示模型、输入/输出/缓存与最后记录的上下文大小 | 请求明细、多模型分项、本次 / 含子任务的范围、来源与覆盖情况 | 模型变化与请求归属保留；上下文大小不是累计消耗 |
| 缺失、部分读取、加密、错误 | 在受影响处简短说明，保留已有可读内容 | 原因、可用范围、重试或其他确实存在的查看路径 | “尚未加载”“没有记录”“不可读取”是不同状态 |

### 默认折叠的边界

主阅读流保留请求、可读回复、重要协作节点和上下文变化。过程区可以包含很多调用，
但不能让读者为了看结果必须先展开它。仅有工具活动的 assistant 也保留过程入口。
中间错误若影响理解，应在折叠入口可见；详情仍留在发生位置。

结构化问答应优先显示问题与回答；解析属于 provider 边界。未支持的结构保留原文，
不把 XML 包装、内部 request ID 或 JSON 键名当作最终设计语言。

## 4. 异步关系如何可视化

主阅读流承载内容，局部连接承载关系。连接不是装饰；每条线必须有可解释的对象与端点。
读者先看到“谁接手了什么”和“带回了什么”，再通过关系理解这两处属于同一件事。
任务名、人员/Agent 身份、方向和动作在节点上可读；只画连线或可点击的点不算讲清协作。

- 在 dispatch、follow-up、返回的原位置插入紧凑节点。节点可选择同一任务，支持键盘操作。
- 默认保持局部关系可见；选中任务时强调该任务的相关节点和局部连线，其他关系降低权重。
  跨屏连接通过“查看分派”“查看这次返回”等文字入口保持可达，不要求读者追随整屏长线。
- 同一任务多次继续和返回使用同一身份；每一次交互仍有独立来源锚点。
- 正文协作区域直接解释相关分工与交接，选中后就地展开该成员或该次往来。
  下一版沿正文分支深化，分别标明分派归属、成员交接与异步返回；大量成员按工作局部展开。
  按需全局概览帮助找到跨回复的任务；完整子历史仍在正文阅读。
  仅有足够时间证据时补充时间范围，无协作记录时不显示空关系区域。
  此规则取代 2026-09-17 样稿 3 以右侧栏承载协作主要内容的选择。
- 正文边上的线表示记录顺序及关联，**线长不表示执行时长**。
  时间概览只有在记录支持时才表示时间范围；观察到的活动跨度不命名为 CPU 时间或连续运行时长。
- 无时间戳保留记录顺序；只有时间接近没有关系证据时不连线。
  只有子会话完成记录而没有父侧接收记录时，不能补出“已交付”的父侧节点。
- 紧邻且同类的高密度交互可以折叠为一段，必须保留数量、范围和展开路径；不能跨越用户输入、
  结果返回、任务中断或上下文变化，把重要转折抹平。

这里“可视化”的验收对象是读者能认出分派、并行、继续与返回的关系。
表格适合精确数值比较，列表适合目录和同类记录检索；复杂运行关系优先使用局部连接或时间概览。

### 一段完整工作应怎样被读懂

例如，用户提出修改要求，主 Agent 分派实现与审查，随后继续检查别的文件；实现结果稍后返回，
主 Agent 追加要求，审查意见又在后续一轮到达。默认阅读应保留这些转折及结果的可读内容。
展开某个任务后，可以读到它从最初要求到后续往来的完整过程；关闭后仍停在原会话位置。
选中任务时，局部关联和侧栏帮助找到历次分派与返回，而非要求读者去事件列表拼装这段故事。

后台命令采用同一阅读原则：看清启动、转入后台、主会话继续、结果返回与如何处理。
完成、收到结果、主 Agent 采用结果可能发生在不同位置，按实际保存的经过分别呈现。
这种例子用于定义体验，不作为合成结果插入用户的真实会话。

## 5. 阅读与导航行为

| 用户操作 | 应发生什么 | 保留什么 |
| --- | --- | --- |
| 打开子会话 | 在相关协作节点附近展开完整子历史；没有位置证据时放在正文末尾并明确标注；有独立打开入口 | 父历史、父阅读位置及折叠状态 |
| 返回祖先历史 | 子历史入口展示祖先路径，选择某层即收起其后代；窄屏各层正文等宽 | 已有位置恢复到原入口；复制链接没有旧位置时，定位到记录中的入口 |
| 从另一节点再次打开同一子会话 | 定位已经打开的同一正文，并定位有证据的目标；不复制第二份 | 同一 canonical child 的搜索、续读及阅读状态 |
| 关闭子会话 | 回到启动该阅读操作的位置，恢复触发控件的键盘焦点 | 父滚动位置与父搜索；关闭不会改变 provider 数据 |
| 打开多级子任务 | 保留祖先导航；窄屏用全宽子阅读层和面包屑，避免无限缩进 | 每一级返回位置；独立链接可复现当前子会话 |
| 点击“查看来源” | 定位被点击的那条原始记录 | 来源 owner；不把“看父侧消息”和“打开子历史”混成一个操作 |
| 搜索 | 明确选择主会话或一个已打开的子会话；检索该范围完整的可用自身历史 | 每个范围各自的词、结果和当前位置；切换或关闭范围后无残留高亮 |
| 搜索命中折叠 / 未加载内容 | 展开相关过程并加载命中的内容，滚动到准确来源 | 查询词、owner 与覆盖范围说明 |
| 点击目录 | 定位请求、agent 回复或唯一任务入口；跟随当前阅读范围高亮 | 子任务和其子会话不重复成为两项；继承背景不进入自身目录 |
| 复制链接、刷新、后退 / 前进 | URL、内容 owner、页面标题与管理操作保持一致 | 可复现的 canonical 内容位置；父子导航不会留下另一会话的导出或恢复命令 |
| 在当前页打开新的原生锚点链接 | 首次跳转到该条来源；随后后退 / 前进恢复各自读到的位置和焦点 | 每次浏览器访问记录独立的阅读位置；已经打开的来源保持正确归属 |
| 读取更多 / 新记录到达 | 就地续读；新记录可用时提供可发现的入口 | 当前阅读锚点，避免强制滚到末尾 |

页面地址中的会话是页头、导出、管理与恢复操作的共同归属。就地阅读子历史时保留该页面归属，
子历史的标题、来源和独立打开入口说明其自身归属；URL 中的阅读位置参数用于复现打开的子历史。
独立打开才切换整个页面所属会话。返回父历史保留搜索、展开状态与已读取内容，不依赖浏览器缓存。

搜索契约首先覆盖“主会话或明确选中的子会话”。整个协作家族的跨会话搜索是后续能力，
只有实际提供完整范围检索时才能在 UI 中声称支持。继承背景保持单独范围，不混入上述结果。

## 6. 数据质量与技术详情

本节约束实现和检查口径。页面以用户理解当前内容所需的信息为先，其余规则在技术详情中可查。

- 自身新增用量按本次执行拥有的请求计数；复制到子会话的历史 usage 记录不再次累计。
- 子会话实际发起的新模型请求，其输入（包括重新发送的共享背景）、缓存读入与输出仍是这次请求的用量。
  不能因内容相同而跨独立请求扣掉实际消耗。
- 总输入、未缓存输入、缓存读入和输出有清楚标签；缓存包含关系按 provider 归一化契约表达。
  缺少字段不当作零。请求合计与单次上下文长度分别呈现。
- “本会话”和“含子任务”分开；家族累计按 canonical 会话和拥有的请求计一次，展示覆盖情况。
  无法解析继承边界或关联缺失时，明确口径不完整，不能展示虚假的精确去重值。
- task 完成数不换算为目标完成百分比。没有结构化 goal 时，呈现原始请求即可。
- 原文、原文摘录、provider 明确记录、派生关系有可查询的区别。
  UI 不生成未经标识的“最新成果总结”，也不把不可解码返回替换成猜测正文。

## 7. 视觉、交互和实现边界

正文先于工具栏、指标和技术标签。左对齐、稳定行宽；中文长文、代码、表格分别使用合适的排版。
标题、操作、阅读正文采用清楚的层级；低频导出、管理和技术诊断收进次级菜单。
无协作的短会话自然退化为清晰的阅读页，不留下空关系框或空目标面板。

颜色之外还用名称、位置和文字状态表达关系。所有关键操作支持键盘，焦点可见；
折叠状态能被辅助技术读取。窄屏保留全部内容与导航能力，代码局部溢出不拖宽整个页面。
动效只解释用户触发的变化，并遵循 reduced-motion。

Provider 负责语义和证据归一化；共享阅读投影负责身份、归属、顺序和覆盖；浏览器负责布局与交互。
沿用 SSR、原生 JavaScript/CSS 和现有协议；只有实际消费者缺少事实时才扩展契约。
现有模型不能表达的呈现要求，先记录缺口及所有权，再实施，不能在浏览器里猜 provider 语义。

## 8. 可检查的验收场景

以下是重构完成的必验场景。通过自动化不替代用户对实页阅读与美观的验收。
优先检查读者能否在默认页面理解请求、回复和关键转折，并通过有意义的入口读完任意细节。
记录可达、来源链接正确或协议通过测试，分别是完整性与工程检查，不能单独代表呈现目标完成。

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| P1 | 从会话库找到旧工作 | 通过可读标题、项目或搜索识别；过滤后进入阅读，再返回保留查找上下文 |
| P2 | 只有一问一答 | 首屏直接理解请求和回复，不被空框、过程工具栏或统计占据 |
| P3 | 多轮工具执行、未知 message phase | 已知过程默认收起且完整可达；未知文本不丢；reasoning 归属不串位 |
| P4 | 分派后主任务继续、两子任务并行 | 默认可读出谁负责什么、主任务期间做了什么、各自带回什么；关联帮助往返，继续同一任务不产生重复身份 |
| P5 | 同一任务两次 follow-up、两次返回 | 能按人/Agent 及时间读懂每次要求与结果；内容分别完整可读，子侧完成与父侧接收不混同 |
| P6 | 打开、关闭、多级子历史 | 完整自身历史可读；父位置与焦点保留；无重复正文和 DOM ID |
| P7 | Compact、长保留上下文和 memory 产物 | 结果优先；续读到最后一条；无产出/加密说明准确；不虚构主上下文变更 |
| P8 | 子会话带共享背景 | 默认折叠；可完整续读；自身 ToC、搜索和新增 usage 不重复计入 |
| P9 | 长历史和延迟加载 | 后页长工具输出可被完整范围搜索命中并定位；未加载、部分覆盖和加载失败可区分 |
| P10 | 来源链接与浏览器历史 | 主/子来源刷新和后退后，URL、正文、标题、导出、管理、恢复操作 owner 一致 |
| P11 | 桌面、中英、明暗主题 | 正文与协作均可读；键盘焦点、对比度和 reduced-motion 实测 |
| P12 | 各 provider、缺失记录与不存在的 child | 当前真实数据和 fixtures 分别注明；没有记录仍可理解，明确缺失而不补造关系 |
| P13 | 团队与成员间合作 | 可看懂成员分工、谁向谁提出要求或交接、结果如何汇入主线；展开对应完整往来 |
| P14 | 后台程序或异步执行 | 可看懂启动/分离、主线继续、结果返回与后续处理；展开全部可用日志，普通进程不被画成子 Agent |
