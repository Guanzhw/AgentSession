# 协作进入正文：呈现方式调研

更新：2026-09-21。状态：用户已确认 A＋乙方向及样稿，正式 Reader 已实现并完成桌面验收。
第 1–9 节保留研究与选择过程；当前交付见第 10 节。

## 1. 要解决的阅读问题

AgentSession 面向回看完整会话的人。用户希望协作在阅读正文时可以理解，同时指出当前
重复助手壳、隐藏的用量、分离的目录和团队侧栏使信息过于分散。本次只研究其中的协作呈现，
不把“进入正文”提前等同于“在正文插入一张完整团队图”。

读者需要连贯回答：主 Agent 把什么交给谁，主线随后做了什么，成员之间怎样交接，
什么结果在何处返回，以及在哪里继续读具体对话。默认内容应能回答这些问题，完整历史可就地展开。

## 2. 案例观察与可借鉴之处

| 案例 | 官方资料中的行为 | 对本项目的启发与取舍 |
| --- | --- | --- |

| [Linear 评论与讨论串](https://linear.app/docs/comment-on-issues) | 回复围绕一条评论组成讨论串；解决讨论时可以选择某条回复作为显露的结论 | 从原文发出分支，并让结果容易找到；本项目优先呈现已保存的结果原文，不依赖重新生成摘要 |
| [Slack threads](https://slack.com/help/articles/115000769927-Use-threads-to-organize-discussions) | 讨论串锚定消息，回复可以选择发送回频道 | 可借鉴“从主线分出、结果回到主线”的关系；核心合作不应只剩侧栏入口 |

| [Honeycomb Agent Timeline](https://docs.honeycomb.io/investigate/observe/agent-timeline) | 跨 trace 汇集会话，按 Agent 组织时间泳道，可展开操作并选择 span 查看详情 | 适合解释“同时发生什么、谁在等待、何时返回”；时间轴作为局部按需视图，长正文仍按阅读流呈现 |
| [GitHub PR 评论](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/commenting-on-a-pull-request) | 文件/行评论可从 Conversation 或 Files changed 继续回复 | 同一内容可从关系入口或原位置抵达；借鉴双向定位，不增加必须来回切换的主页面 |

## 3. 不同问题使用不同表达

下表是本项目的候选设计，不是上述产品已经验证的组合。

| 读者想知道 | 适合的表达 | 默认层应保留什么 |
| --- | --- | --- |
| 谁负责什么 | 紧凑成员/任务标注；复杂归属可展开局部关系图 | 成员名、职责或任务目的；避免只显示成员计数 |
| 谁把什么交给谁 | 带内容标签的有向交接线 | 发出者、接收者、交接内容及对应结果入口 |
| 何时分离、何时回来 | 正文分派/返回锚点，以同一任务身份互相定位 | 主线中间的工作与真实返回位置 |
| 哪些工作同时进行 | 局部时间泳道 | 仅在需要看并行关系时展开；缺少时间记录则只表达已知顺序 |
| 究竟说了什么、做了什么 | 原文、讨论分支与完整子历史 | 可读结果；具体往来和执行过程逐层展开 |

“主 Agent 安排 writer 和 reviewer”是一组分派；“writer 把候选稿发给 reviewer”是消息交接；
“reviewer 将审校结果发回主 Agent”是返回。一个无标签的 `主 Agent → writer → reviewer`
会混淆这三件事。图的价值在于减少这种理解成本，而不是增加节点数。

## 4. 三种同内容样稿候选

所有样稿保持相同正文、字号、阅读宽度和默认可见结果，只改变协作区域的组织方式。

| 候选 | 正文中的安排 | 优势假设 | 需要实页判断的代价 |
| --- | --- | --- | --- |
| A：正文分支 | 分派旁出现紧凑任务分支；原位置保留返回及结果；展开分支阅读完整子历史 | 连续阅读自然，跨轮工作不会被挪成另一页 | 同级成员之间的往来是否仍不明显；多分支是否造成深缩进 |
| B：局部交接带 | 在相关合作片段放一条紧凑交接链，节点含职责，边标交接内容；点击就地展开该次往来 | writer → reviewer → 主会话一眼可读，信息集中 | 是否与相邻原文重复；多人反复往来时能否保持紧凑 |
| C：局部泳道 | 相关片段可展开“主线 / writer / reviewer”泳道，按时间放分派、交接和返回 | 并行、等待与晚到结果易比较 | 时间轴和长文本是否抢空间；默认展开是否打断阅读 |

2026-09-20 的初步假设是以 A 为阅读骨架，比较 B、C 的补充价值。
该轮候选的用户反馈及当前推进方向见第 7 节；不再将 B、C 作为与 A 并行推进的整页候选。

### 连续历史中的放置规则

- 分派处说明任务目的和成员。结果在实际返回处呈现，分派与返回可互相定位。
- 后续查询、催办、再次分派到同一任务的记录保持同一身份，每次往来仍可独立阅读。
- 正文默认展示当时已经发生的活动；如在早期入口显示整段工作的后续概览，应明确标为
  “这项任务的后续”，避免把未来结果误当作此处已收到的回复。
- 成员交接先呈现发送者、接收者及可识别的内容，展开后阅读完整消息。关系图与成员列表
  不重复铺开同一信息；侧栏不承担理解当前合作的必经步骤。
- 多次高密度往来可以局部分组，但用户补充、失败、恢复和结果返回保持可见。
  子任务完成与主线接收分开保留；没有接收记录时不补造返回点。

## 5. 选择与交付步骤

1. 固定两段现有内容：本次原生 DSH 的 writer/reviewer 合作，以及已有 Codex 跨轮异步片段。
   从已保存历史取材，不重新生成付费模型样本。另用现有多次往来样本检查复杂度。
2. 在相同阅读外壳中比较 A、A+B 与 A+C；每份样稿都展示默认态和一次展开态。
   展示截图及可操作入口，不能只交付术语或架构说明。
3. 逐项回答：能否看出谁分派给谁、交接了什么、主线中途做了什么、结果在哪里返回；
   能否展开完整对话并回到原处。记录首屏内容、重复文字、展开次数和跳转次数。
4. 将推荐样稿交给用户判断阅读与外观，再更新呈现契约的具体形式并实施 R3。
   工程正确性检查与用户的视觉认可分开记录。

调研阶段只更新研究、契约和计划。R1 的过程合并与用量、R2 的常驻目录当时保留在交付队列；
R3 增加样稿比较步骤，不直接将现有侧栏团队图搬进正文。

## 7. 用户反馈与下一版方向（2026-09-21）

以下是用户陈述的阅读体验，不是代理通过新截图完成的审查：

- A 正文分支相对最简洁、有条理，但团队协作与异步推进的连接关系没有区分清楚。
- B 分支加交接带虽然增加内容，却没有形成明确的视觉焦点。
- C 分支加泳道难以理解；当成员增至几十名时，为每人展开泳道不可取。

下一版保留 A 的紧凑阅读骨架，重点验证三个连接语义：

| 关系 | 需要读懂的内容 | 候选表达 |
| --- | --- | --- |
| 分派与归属 | 谁安排谁做什么，同一工作包含哪些成员 | 任务旁的紧凑分支，保留目的与成员；建立任务和启动成员分别说明 |
| 成员间交接 | 谁将什么内容发给谁 | 相关正文处的短方向连接，标明交接内容；展开该次完整往来 |
| 异步延续与返回 | 同一任务何时分出，主线如何继续，结果何时回来 | 分派和返回处共享任务身份，双向定位；当前选中任务局部强调，不要求追踪跨屏长线 |

团队协作和异步执行可以同时发生：同一个团队成员既有成员/通信关系，也有自身任务的
分出、继续和返回过程。上述关系通过位置、连接形态和动作文字共同表达，不只用颜色区分。

视觉焦点首先是相关工作的动作或结果，例如“审校完成：字数更正为 26”；成员、时间和
连接作为次级说明。正文继续保留实际结果，不将注意力全部放在成员名称和等权节点上。

大量成员按已记录的工作归属分组，默认露出与当前阅读片段有关的关系。其余成员及过程
逐层展开、可搜索定位；同一 Agent 的多次参与保持身份。少量成员和几十名成员都应保持
正文行宽稳定。密集布局压力样本与真实 provider 历史分开标识，不重新生成付费模型样本。

下一步只制作深化 A 的完整桌面样稿，检查关系辨认、焦点和密集成员的展开方式。
用户对 A 的相对偏好不等于已认可其外观，也不等于已经通过跨轮或大规模协作验收。

## 9. A＋乙交互样稿（2026-09-21）

入口：`tmp/collaboration-comparison/reader-preview.html`。源文件为同目录的
`reader.html`、`reader.css`、`reader.js`；`build-reader.mjs` 将已有 `samples.js`、样式和
本地 Lucide 图标内嵌成单文件，旧的三候选比较页保留。没有修改产品源码或 provider 数据。

| 内容 | 此版呈现 |
| --- | --- |
| 请求与回复 | 连续正文；相邻主会话文字共用紧凑抬头，保留独立事件锚点；请求节选可展开原文 |
| 分派 | 工作名优先，主会话与负责成员次级；关键行直接可见，原文或不可读正文说明按需展开 |
| 成员交接 | 工作/结果摘要为焦点，短方向连接表示发送方与接收方；点击直接读该次完整交接正文 |
| 子会话结果 | 与主回复分开标明；仅有同一关联 ID 的早先分派时提供双向定位，不将完成当作主线投递 |
| 普通过程 | 相邻执行在正文局部集中；投递回执、原始 JSON 保留在次级入口 |
| 导航 | 左侧常驻请求、回复与任务目录；包含冒号的真实 ID 以完整 ID 定位，展开全部祖先后聚焦 |
| 成员规模 | 默认最多三项分派，其余局部展开；结构测试使用 60 项合成工作，不作为真实历史或并发依据 |

验证命令：`node --test tmp/collaboration-comparison/reader.test.mjs`，14/14 通过；
`node tmp/collaboration-comparison/build-reader.mjs` 生成单文件并检查脚本语法、静态锚点及图标内嵌；
`npm run review` 治理与类型检查通过。控制器测试使用模拟 DOM，不等同于浏览器操作验收。

本版仍只有原有两段真实摘录。Codex 是同一用户请求内的委派与后续结果，尚无跨用户轮次
样本；其两名 reviewer 的分派不在片段中，不补画起点。完整会话与完整子历史通过原 Viewer
入口阅读，样稿只在原位展示已捕获的正文。模型仅使用样本已提供的字段，未编造用量。

制作样稿时本地预览访问未恢复，没有把静态检查计为浏览器验收。
用户随后在该样稿回复“行”；正式产品的 HTTP Reader 另行完成下面的验收。

## 10. 正式 Reader 落地（2026-09-21）

R1–R4 已集成：纯执行合并与直接用量、桌面常驻目录、正文局部分派/交接/收到消息、
More 技术入口。DSH 原生双成员合作和 Codex 跨用户轮次的返回已在正式页面逐项展开；
