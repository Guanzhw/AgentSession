# Pi native Session Protocol v3 (0.85.1)

## Context

Pi's official npm package is 0.85.1 with package tag/gitHead
`d981de1229ef899957bbe968bc8dcda02a21f477`; the independent upstream HEAD is
`f53ac1135149f03fd1e2a5bfd29861120eaf5b96`. The session format remains v3.
The Windows installation is 0.80.10 and has no live 0.85.1 transcript, so the
new fields are verified from official source/docs, bounded fixtures, and the
adapter boundary. The previous 0.84.4 decision remains a historical snapshot.

## Decision

Pi constructs native v3 from the same cached file-store entry and finalized v2
snapshot used by `getSessionProtocol()`. It copies all v2 facts exactly and
adds only provider-recorded evidence:

- one request-scoped Usage record per top-level assistant entry, deduplicated
  by `responseId` and otherwise keyed by entry id; request components normalize
  reasoning as an output subset and do not add `cacheWrite1h` a second time;
  contradictory explicit totals are null, and all-zero deferred/pending
  markers are suppressed;
- readable active compaction and `branch_summary` summaries become bounded
  Context versions and transformations connected to the existing v2 event and
  artifact; abandoned operations do not produce active results;
- Work, Execution, and Coordination remain `not-observed`, with no invented
  Task, AgentRun, actor, delivery, handoff, or origin slice;
- branch heads bind to a canonical event only when the matching source entry
  exists; otherwise the head is null;
- parser metadata preserves bounded deferred presence and terminal facts:
  only `stopReason=deferred` is terminal, while official `pending` is not.

The current official context boundary is `firstKeptEntryId`. `retainedTail`
is historical/harness extension evidence only: it is count metadata and never
an independent message, context version, or token request.

## Alternatives considered

- Reuse Pi's billed session total as request Usage. Rejected because aggregate
  and nested usage have no stable assistant-request identity or cardinality.
- Treat `retainedTail` as a current context field. Rejected because current
  official context construction uses `firstKeptEntryId`; retainedTail is only
  historical/harness evidence.
- Bind a raw branch head entry id directly to a protocol event. Rejected because
  protocol references must use the canonical event id, and missing matches must
  remain null.

## Boundaries

Provider-owned parsing and protocol construction remain in `src/providers/pi/`;
shared runtime code receives the finalized typed v3 snapshot and does not gain
a Pi-specific branch. Pi provider files and transcripts are read-only. No
provider aggregate or nested tool/summary usage is promoted to a request
UsageRecord without stable request identity/cardinality.

## Consequences

Runtime Workbench can display Pi's recorded assistant-request usage and active
context-summary results while retaining the existing v2 conversation and
branch facts. Coverage stays explicit when Pi has no evidence for work,
execution, coordination, or context results. Session billed totals remain a
separate provider statistic and are not misrepresented as request-level usage.

## Verification

- `npm run review` passed (governance and typecheck).
- Focused compiled-source tests passed for `test/pi-native-v3.test.mjs` and
  `test/pi-format-v3.test.mjs`, including response-id deduplication, usage
  normalization, aggregate exclusion, active/abandoned context, canonical
  branch heads, and `pending` non-terminal metadata.
- An independent Luna review found and the implementation corrected two
  identity/topology gaps: response and entry fallback identities are now
  namespaced with the active event-bound response preferred, and a trailing
  tool-result entry resolves through its canonical tool-call event. The same
  review also identified and corrected stale active Pi version references.
- `npm test` passed all 483 tests after the review fixes.
- The real Windows Pi session was inspected read-only; its transcript size and
  mtime were unchanged. The adapter/full-protocol smoke returned v2 and v3
  validation success, canonical branch head `event:223048a9`, one observed
  request usage record, and no protocol warnings/errors. No live 0.85.1 data
  was claimed.
- The live Runtime Workbench showed the single 4,995-token request, explicit
  `not-observed` coverage for Work, Execution, Coordination, and Context, and a
  two-entry conversation ToC. At 390 px and 320 px viewport widths there was
  no horizontal overflow, console output, or page error.
